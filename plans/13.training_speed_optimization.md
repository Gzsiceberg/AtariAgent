# AtariAgent Training-Speed Optimization Plan

## Goal

Reduce learner update wall time while preserving EfficientZero training behavior and learning quality. The current training workload performs 100,000 collection-phase updates followed by 20,000 learner-only updates, so update throughput dominates total runtime.

## Current observations

- Hardware: NVIDIA RTX 3090 with 24 GiB VRAM. PyTorch reports native BF16 support on this GPU.
- A sampled active run used about 7.3 GiB VRAM, approximately 45-50% GPU SM utilization, and approximately 25-27% memory-controller utilization.
- The learner runs in full FP32 without autocast or gradient scaling.
- cuDNN benchmarking is disabled and deterministic cuDNN behavior is forced.
- Runtime `jaxtyping`/`beartype` checks wrap frequently called model and loss functions.
- Replay sampling constructs batches through Python and copies every batch tensor synchronously to the GPU.
- `ReplayBatch.normalized_observations()` reconstructs all `unroll_steps + 1` observations, but `Trainer.train_step()` only consumes the root observation.
- With batch size 256, six states, twelve input channels, and 96x96 images, the current normalized observation tensor is about 648 MiB in FP32. The root observation alone is about 108 MiB.
- Scalar categorical loss performs two complete cross-entropy operations for each interpolated target.
- Loss metrics are converted to Python scalars every update, producing unnecessary CPU/GPU synchronization when they are only printed every `training.log_every` updates.
- Both local EfficientZero reference repositories use automatic mixed precision. EfficientZeroV2 additionally uses `torch.compile`.

## Guiding rules

1. Measure each optimization independently before combining changes.
2. Separate performance-only changes from algorithm-changing configuration changes.
3. Keep a deterministic FP32 mode for debugging and regression testing.
4. Validate not only numerical correctness but also self-play and evaluation reward curves.
5. Do not reduce total updates, batch size, or unroll length until implementation-level optimizations are exhausted.

## Phase 0: Establish a performance baseline

### Add opt-in timing instrumentation

Measure these sections separately:

1. Prioritized replay sampling and Python batch construction.
2. CPU-to-GPU batch transfer.
3. Root observation reconstruction and normalization.
4. Model forward and loss construction.
5. Backward pass.
6. Gradient clipping and optimizer step.
7. Priority transfer back to CPU and replay priority update.
8. Logging, checkpointing, and evaluation overhead.

Use CUDA events or synchronized profiler regions for GPU timings. Do not synchronize every update during ordinary training; enable detailed timings only in a profiling mode.

### Record baseline metrics

- Updates per second.
- Training samples per second.
- Mean and p95 update duration.
- GPU SM and memory utilization.
- CPU utilization.
- Peak allocated and reserved CUDA memory.
- Replay sampling duration.
- Host-to-device transfer duration.
- Forward, backward, and optimizer durations.

Benchmark after a warmup period with fixed tensor shapes. Exclude initial CUDA setup, `torch.compile` compilation, checkpoint writes, and evaluation episodes from steady-state measurements.

### Baseline correctness data

Save a short deterministic FP32 run containing:

- Initial and final losses.
- Gradient norms.
- A few model parameter checksums.
- Priorities from selected batches.
- Self-play reward statistics.
- Evaluation rewards from representative checkpoints.

## Phase 1: Stop constructing unused observations

This should be the first code-level optimization because it is low risk and removes demonstrably unused work.

### Root-only normalization

Add a replay-batch operation that reconstructs and normalizes only the initial frame stack. Update `Trainer.train_step()` to call it directly instead of constructing all overlapping observations and then selecting `observations[:, 0]`.

Affected areas:

- `src/atariagent/replay.py`
- `src/atariagent/training/learner.py`
- Replay and learner tests

### Required tests

- Root-only output must exactly equal `normalized_observations()[:, 0]` in FP32.
- Support RGB and grayscale observations.
- Support different frame-stack and unroll lengths.
- Preserve shape, device, and normalization range.
- Confirm trainer losses and gradients remain unchanged for a fixed batch.

### Follow-up: avoid sampling unused future frames

The current learner does not use image observations after the root because it unrolls latent dynamics and has no observation-consistency loss. Replay currently builds and transfers future frames anyway.

After root-only normalization is verified, consider a learner-specific replay sampling path that includes only the root frame stack. This requires care because `ReplayBatch.stack_size` is currently inferred from frame count and unroll length. Prefer explicit metadata or a separate compact training-batch representation rather than weakening shape invariants.

Expected result:

- Much lower temporary GPU memory.
- Less GPU conversion and stacking work.
- Less CPU batch construction and host-to-device traffic after the follow-up change.

## Phase 2: Add mixed-precision learner updates

Mixed precision is likely the largest single speed improvement on the RTX 3090.

### Configuration

Add an explicit precision setting rather than silently changing behavior:

```yaml
training:
  precision: fp32  # fp32, fp16, or bf16
```

Keep `fp32` available for debugging. Use BF16 autocast as the initial optimized mode because the RTX 3090 supports BF16 Tensor Core execution. BF16 has the same exponent range as FP32, making overflow and underflow much less likely than with FP16, and it normally does not require gradient scaling. Keep FP16 autocast with `GradScaler` as an alternative compatibility mode because it matches the EfficientZero reference approach.

Recommended evaluation order:

1. BF16 autocast as the preferred production mode.
2. FP16 autocast with `GradScaler` as a reference-compatible alternative.
3. FP32 as the deterministic debugging and numerical baseline.

### Trainer behavior

- Wrap model forward and loss construction in CUDA autocast using the configured dtype.
- For BF16, call `loss.backward()` and `optimizer.step()` normally without a scaler.
- For FP16, use `GradScaler`, unscale before gradient clipping, step through the scaler, and update the scaler after each optimizer step.
- Keep master parameters and optimizer state in FP32 for both mixed-precision modes.
- Ensure numerically sensitive reductions and categorical losses use safe dtypes; autocast should be allowed to retain FP32 where required.
- Decode root values for priorities without introducing unsupported low-precision operations.
- Detect unsupported BF16 hardware and fail clearly or require an explicit fallback rather than silently changing precision.

### Checkpoint behavior

Persist scaler state only for FP16 training so resumed runs preserve their dynamic loss scale. BF16 and FP32 checkpoints do not require scaler state. Loading older checkpoints should remain possible when scaler state is absent.

### Validation

- Confirm `torch.cuda.is_bf16_supported()` before selecting BF16.
- No NaN or infinite losses, gradients, model states, or priorities.
- For FP16, verify gradient clipping occurs after scaler unscaling.
- Compare FP32, BF16, and FP16 loss trajectories over a short fixed-data run.
- Compare BF16 and FP16 steady-state throughput and peak memory; do not assume one is faster on every kernel.
- Compare self-play and evaluation reward trends rather than requiring bitwise equality.
- Measure update throughput and peak memory after warmup.

Expected result: approximately 1.5-2x learner throughput is plausible for either mixed-precision mode, but actual improvement must be measured. Prefer BF16 when throughput is comparable because of its wider numerical range and simpler training path.

## Phase 3: Add a fast backend mode

The current script explicitly prioritizes determinism over speed:

```python
torch.backends.cudnn.benchmark = False
torch.backends.cudnn.deterministic = True
```

### Configuration

Add a clear mode such as:

```yaml
training:
  deterministic: true
```

For performance runs:

- Set deterministic mode to false.
- Enable cuDNN benchmarking for fixed convolution shapes.
- Enable high float32 matmul precision/TF32 where appropriate.
- Retain fixed random seeds, while documenting that exact reproducibility is no longer guaranteed.

### Validation

- Benchmark only after cuDNN autotuning has completed.
- Verify no significant reward regression over multiple seeds.
- Keep deterministic mode as the CI and debugging default if desired.

## Phase 4: Remove Python overhead from model hot paths

### Runtime type checking

`jaxtyped(typechecker=beartype)` is valuable during development but runs on every decorated call. Dynamics and prediction execute repeatedly during each five-step unroll.

Introduce a production-training switch that disables runtime tensor type checking while retaining:

- Static annotations.
- Explicit critical validation at API boundaries.
- Full runtime checks in tests and debug runs.

The switch must be established before decorated modules are imported, or the decorator selection should be centralized in a project helper.

### Reduce repeated Python work

- Avoid repeatedly changing all modules to training mode when they are already in training mode.
- Avoid rebuilding constant support tensors where caching is safe.
- Avoid constructing Python tuples and lists from CUDA tensors unless the CPU replay buffer requires them.
- Compute detailed metrics only on logging updates.

### Validation

Run the complete test suite with runtime checks enabled. Add a smoke test with checks disabled to ensure the production path remains valid.

---

## Phase 5: Introduce `torch.compile`

Apply compilation only after reducing runtime decorators and other graph breaks.

### Initial scope

Compile model computation rather than the entire training script:

- Representation network.
- Dynamics network.
- Prediction network.
- Potentially a trainer forward/loss function with fixed unroll length.

### Risks to handle

- Preserve checkpoint state-dict key compatibility.
- Avoid recompilation from changing shapes or Python control flow.
- Verify optimizer parameters still reference the compiled model parameters.
- Avoid compiling logging, replay sampling, checkpointing, or evaluation orchestration.
- Expect the first updates to be slower because of compilation.
- Check graph-break reports before judging performance.

### Benchmark method

Compare eager and compiled steady-state throughput after sufficient warmup. Report compilation time separately.

## Phase 6: Improve replay sampling and transfer

The replay buffer performs prioritized sampling, trajectory lookup, sample construction, and tensor stacking in Python for every update.

### Profile before refactoring

Determine whether replay sampling and transfer are a significant fraction of update wall time after mixed precision. Faster GPU compute may expose the data pipeline as the next bottleneck.

### Prefetch pipeline

- Prepare the next replay batch while the GPU trains on the current batch.
- Use a bounded prefetch queue to avoid excessive memory use.
- Preserve deterministic replay RNG ordering when deterministic mode is enabled.
- Do not mutate replay structures concurrently without synchronization.

### Pinned memory and asynchronous copies

- Pin CPU tensors used for CUDA transfer.
- Transfer with `non_blocking=True`.
- Optionally use a dedicated CUDA stream for host-to-device copies.
- Synchronize the training stream only when the batch is consumed.

### Vectorize sample construction

Longer-term options:

- Maintain indexed arrays for trajectory locations instead of repeatedly scanning Python structures.
- Pre-store compact tensor blocks where memory permits.
- Batch frame and target gathering with NumPy or PyTorch indexing.
- Avoid many small tensor allocations inside `_make_sample()`.

### Validation

- Sample probabilities and importance weights remain correct.
- Stable transition IDs still update the intended priorities.
- Terminal padding and continuation across trajectory blocks remain unchanged.
- Deterministic mode reproduces the same sampled IDs.

## Phase 7: Reduce loss-kernel count

### Optimize interpolated categorical scalar loss

`ReplayBatch._scalar_loss()` currently calls full cross-entropy twice: once for the lower support atom and once for the upper support atom.

Equivalent optimized approach:

1. Compute `log_softmax(logits)` once.
2. Gather the lower and upper atom log probabilities.
3. Weight the two gathered losses by interpolation weights.

This removes one support-wide reduction per scalar loss call. With root and recurrent value/value-prefix predictions, this can eliminate many redundant kernels per update.

### Required tests

- Match the existing implementation over random logits and targets.
- Test exact support atoms, fractional transformed targets, support boundaries, and masked targets.
- Compare forward values and gradients in FP32.
- Verify behavior under autocast.

---

## Phase 8: Remove avoidable synchronization

### Metrics

The trainer currently converts losses and gradient norms to Python floats every update. Only perform detailed conversions when:

- The update is logged.
- A checkpoint requires the values.
- Profiling is enabled.

Maintain lightweight tensor metrics otherwise.

### Priorities

Prioritized replay currently requires root priorities on the CPU each update. Keep one intentional synchronization for this path unless replay priority storage moves to the GPU or updates are queued asynchronously.

Potential later improvements:

- Asynchronous priority copies into pinned CPU buffers.
- Batched/queued replay priority updates.
- GPU-resident priority sampling, only if profiling justifies the added complexity.

---

## Recommended implementation order

1. Add baseline timers and profiler mode.
2. Reconstruct and normalize only the root observation.
3. Add BF16 autocast as the preferred mode and FP16 plus gradient scaling as an alternative.
4. Add configurable fast cuDNN/TF32 mode.
5. Disable runtime tensor type checking in production runs.
6. Profile again.
7. Add `torch.compile` and inspect graph breaks.
8. Add replay prefetching, pinned memory, and asynchronous transfer if data loading is now limiting.
9. Replace double cross-entropy scalar loss with one log-softmax and gathers.
10. Remove unnecessary per-update metric synchronization.

## Acceptance criteria

### Correctness

- All tests pass in FP32 deterministic mode.
- Root-only observation output exactly matches the old root slice.
- Optimized scalar loss matches old FP32 outputs and gradients.
- Checkpoints remain loadable by training evaluation and `scripts/watch_agent.py`.
- No invalid priorities or NaN/Inf model values.

### Performance

- Report steady-state updates per second before and after every phase.
- Report peak CUDA memory and CPU sampling time.
- Target at least a meaningful improvement from each retained optimization.
- A reasonable combined initial target is approximately 1.5-2x learner throughput, subject to measurement.

### Learning quality

Run at least one short comparison before a full 100k-transition experiment:

- Same environment and seeds.
- Same update, batch, replay, and MCTS settings.
- Compare training losses, self-play rolling raw rewards, and checkpoint evaluation rewards.
- For non-deterministic or mixed-precision modes, compare trends over multiple seeds rather than requiring exact trajectories.

Do not adopt an optimization that improves synthetic update throughput but consistently degrades the Atari learning curve.
