# EfficientZero V2 Atari Implementation Gaps

## Scope

This document records only material differences between this repository and the released Atari implementation in `~/repos/EfficientZeroV2`. MCTS internals are excluded: tree selection, backup, Gumbel behavior, PUCT constants, and simulation-count differences are not assessed.

The EfficientZero V2 README warns that its released Atari branch does not fully reproduce the paper. These findings therefore describe source-code parity with the released repository, not definitive parity with the paper's experiments.

## Major Findings

### 1. Image augmentation is missing

The reference enables `['shift', 'intensity']` augmentation and applies it to both root observations and consistency-target observations. Shift augmentation uses four-pixel replication padding; intensity augmentation applies clipped Gaussian multiplicative noise with scale `0.05`.

The current learner normalizes replay frames and feeds them directly to the representation network. It has no equivalent augmentation configuration or implementation.

Relevant current code:

- `src/atariagent/training/learner.py`
- `configs/train_agent.yaml`

Reference code:

- `~/repos/EfficientZeroV2/ez/config/config.yaml`
- `~/repos/EfficientZeroV2/ez/data/augmentation.py`
- `~/repos/EfficientZeroV2/ez/agents/base.py`

This is a major training difference because consistency learning in EfficientZero is coupled to augmented observation targets.

### 2. The dynamics action encoder does not match

The reference Atari dynamics model enables a 16-channel action embedding. It projects the normalized scalar action plane through a `1x1` convolution, applies `LayerNorm([16, 6, 6])` and ReLU, concatenates the result with the 64-channel latent state, and applies an `80 -> 64` transition convolution.

The current Python and native C++ dynamics models concatenate one normalized action plane directly with the latent state and apply a `65 -> 64` convolution. They do not contain the configured action embedding or layer normalization.

Relevant current code:

- `src/atariagent/models/dynamics.py`
- `cpp/models/dynamics.cpp`

Reference code:

- `~/repos/EfficientZeroV2/ez/config/exp/atari.yaml`
- `~/repos/EfficientZeroV2/ez/agents/models/base_model.py`

### 3. Prediction and value-prefix MLP activations differ

The reference `mlp()` helper uses ELU for hidden layers. This helper constructs the Atari policy, value, and LSTM value-prefix heads.

The current policy, value, and value-prefix heads use ReLU. The native C++ inference models reproduce the current ReLU architecture, so native and Python execution agree with each other but not with the reference.

Relevant current code:

- `src/atariagent/models/prediction.py`
- `src/atariagent/models/dynamics.py`
- `cpp/models/prediction.cpp`
- `cpp/models/dynamics.cpp`

Reference code:

- `~/repos/EfficientZeroV2/ez/agents/models/layer.py`
- `~/repos/EfficientZeroV2/ez/agents/models/base_model.py`

### 4. The consistency prediction head is too wide

The reference consistency prediction head is `1024 -> 256 -> 1024`.

The current default is `1024 -> 512 -> 1024`, and training constructs it without overriding the default. This materially increases the consistency network's parameter count and changes its optimization behavior.

Relevant current code:

- `src/atariagent/models/consistency.py`
- `scripts/train_agent.py`

### 5. The consistency-loss coefficient differs

The released reference Atari configuration uses a consistency coefficient of `5.0`. The current effective configuration uses `2.0`.

Unlike the apparent value-loss coefficient difference, there is no internal factor that makes these consistency coefficients equivalent.

Relevant current code:

- `configs/train_agent.yaml`
- `src/atariagent/training/learner.py`

Reference code:

- `~/repos/EfficientZeroV2/ez/config/exp/atari.yaml`

### 6. Replay warmup uses a different behavior policy and policy target

The reference collects searched actions and searched policy targets from the start. It only delays learner updates until replay contains 2,000 transitions.

During current warmup, search still runs, but the worker replaces the selected action with a seeded uniform-random action and replaces the stored visit target with a uniform distribution. It retains the searched root value. Therefore the first 2,000 transitions have a different behavior policy and different policy supervision.

The current comment stating that this matches EfficientZero replay warmup is not supported by the released reference implementation.

Relevant current code:

- `scripts/train_agent.py`
- `src/atariagent/selfplay.py`

Reference code:

- `~/repos/EfficientZeroV2/ez/worker/data_worker.py`
- `~/repos/EfficientZeroV2/ez/agents/base.py`

### 8. The target-network update schedule and delay semantics differ

The reference publishes reanalysis weights every 200 updates. It publishes the snapshot retained from the preceding interval and only then captures the current online weights for the next publication. Its reanalysis model is therefore delayed by an additional interval.

The current effective configuration publishes an immediate online-network snapshot every 1,000 updates. It differs in both update frequency and model age.

There is also an internal configuration inconsistency: the structured default says 200, while the effective YAML overrides it to 1,000.

Relevant current code:

- `configs/train_agent.yaml`
- `src/atariagent/training/config.py`
- `scripts/train_agent.py`

Reference code:

- `~/repos/EfficientZeroV2/ez/config/exp/atari.yaml`
- `~/repos/EfficientZeroV2/ez/agents/base.py`

### 9. Reanalysis caching changes stochastic target semantics

The reference regenerates reanalyzed targets whenever a transition is sampled.

The current native cache stores the refreshed TD target, search root value, and policy by stable transition ID until target weights change. Because reanalysis uses exploration noise, repeated samples reuse the first stochastic result rather than receiving a new result. Duplicate states within one batch are also deduplicated and share one result.

With the current 1,000-update target interval, a cached noisy policy or search value can remain fixed for up to 1,000 learner updates. This is a semantic change, not only a performance optimization.

Relevant current code:

- `configs/train_agent.yaml`
- `cpp/reanalysis/cache.cpp`
- `cpp/reanalysis/engine.cpp`

Reference code:

- `~/repos/EfficientZeroV2/ez/worker/batch_worker.py`

### 10. Mixed-target freshness has a boundary difference

The reference uses:

```python
sample_idx > collected_transitions - threshold
```

With zero-based indices, this treats 4,999 transitions as recent when the threshold is 5,000.

The current implementation uses transition age and treats exactly 5,000 transitions as recent. The current behavior is more consistent with the stated threshold but is not source-identical at the boundary.

Relevant current code:

- `src/atariagent/replay.py`
- `src/atariagent/replay_batch.py`

Reference code:

- `~/repos/EfficientZeroV2/ez/worker/batch_worker.py`

### 11. Trajectory-tail TD bootstrapping differs

The current replay explicitly retains lookahead transitions and can construct a complete five-step bootstrap for the final sampleable starts of a nonterminal 400-transition block.

The reference pads rewards and observations from the following block, but its episodic bootstrap checks compare against a trajectory length that excludes padded actions. At the block tail, it can retain the padded rewards while omitting the expected value bootstrap.

The current behavior is closer to the documented fixed five-step target, but it is not an exact reproduction of the released source path.

Relevant current code:

- `src/atariagent/selfplay.py`
- `src/atariagent/replay.py`

Reference code:

- `~/repos/EfficientZeroV2/ez/data/trajectory.py`
- `~/repos/EfficientZeroV2/ez/worker/batch_worker.py`

### 12. Initial replay priorities differ

The reference computes initial self-play TD errors and initializes all transitions in a new trajectory to at least the maximum error observed for that trajectory.

The current replay assigns all newly inserted transitions only the existing replay-wide maximum priority. During initial warmup this generally leaves all priorities equal to 1, whereas reference priorities can immediately exceed 1.

Relevant current code:

- `src/atariagent/replay.py`

Reference code:

- `~/repos/EfficientZeroV2/ez/worker/data_worker.py`
- `~/repos/EfficientZeroV2/ez/data/replay_buffer.py`

### 13. Replay capacity and eviction behavior differ

The reference Atari configuration declares a one-million-transition replay buffer, and the released replay implementation does not enforce FIFO eviction.

The current configuration uses a real FIFO capacity of 100,000 transitions. Stable transition IDs make current age calculations robust after eviction, but changed transition budgets, final flushes, or concurrent use can produce replay contents different from the reference.

Relevant current code:

- `configs/train_agent.yaml`

### 14. Loss masking is not source-equivalent

The reference primarily applies one recurrent action mask. It computes policy mismatch masks during reanalysis but does not use those masks in the Atari policy loss.

The current learner separately tracks action, policy, and value validity. It suppresses unavailable policies, preserves valid terminal zero-value targets, and leaves invalid search positions on TD values.

The current behavior is more explicit and robust, but it differs on terminal, truncated, and incomplete trajectory tails.

- `src/atariagent/training/learner.py`

Reference code:

### 15. Numerical precision and AMP behavior differ

The reference uses CUDA FP16 autocast with `GradScaler` for learner updates. It also uses FP16 autocast for self-play, reanalysis, and evaluation inference.

The current effective configuration uses BF16 autocast for the learner and native reanalysis without gradient scaling. Python self-play and evaluation inference run in FP32. Current configuration supports FP32 and BF16, but not the reference FP16 learner mode.

### 16. Environment wrapper ordering changes episode truncation

The reference wrapper order is effectively:

```text
NoopReset -> MaxAndSkip -> EpisodicLife -> WarpFrame -> TimeLimit
```

The current order is effectively:

```text
AtariPreprocessing -> TimeLimit -> EpisodicLife -> FrameStack
```

In the reference, resetting after an artificial life terminal also resets the outer time-limit counter. In the current implementation, the time limit is inside the episodic-life wrapper, so an artificial-life reset does not reset the full-game counter.

This can truncate trajectories at different times. The current behavior better preserves a full-game horizon, but it is not source-equivalent.

The projects also use different environment generations: old Gym `GameNoFrameskip-v4` versus Gymnasium `ALE/Game-v5`. They are configured similarly but are not guaranteed to produce identical observations and reset sequences.

Relevant current code:

- `src/atariagent/selfplay.py`

Reference code:

- `~/repos/EfficientZeroV2/ez/envs/__init__.py`
- `~/repos/EfficientZeroV2/ez/envs/wrapper.py`

### 17. Self-play and learner orchestration have different staleness

The reference uses asynchronous Ray actors, publishes learner weights to self-play workers every 100 updates, and throttles collection based on learner progress.

The current implementation alternates synchronous collection and learning in one process. It typically collects 400 transitions, performs 400 updates, and then collects with the immediately updated model.

This changes:

- Which model version generated each trajectory.
- Replay age at sampling time.
- Batch-target staleness.
- The exact relationship between collected transitions and learner updates.

Relevant current code:

- `scripts/train_agent.py`
- `src/atariagent/training/batch_worker.py`

Reference code:

- `~/repos/EfficientZeroV2/ez/worker/data_worker.py`
- `~/repos/EfficientZeroV2/ez/agents/base.py`
- `~/repos/EfficientZeroV2/ez/worker/__init__.py`

### 18. The rollout temperature schedule switches earlier

The reference computes temperature thresholds over all 120,000 updates, producing transitions at 60,000 and 90,000 updates.

The current training loop passes only the 100,000 collection-phase updates to the schedule, producing transitions at 50,000 and 75,000 updates.

This affects rollout action sampling and therefore the data distribution.

Relevant current code:

- `scripts/train_agent.py`
- `src/atariagent/training/config.py`

Reference code:

- `~/repos/EfficientZeroV2/ez/agents/base.py`

### 19. Evaluation and checkpoint schedules differ

The reference evaluates and saves every 10,000 updates and uses ten evaluation episodes. Its evaluation worker runs asynchronously.

The current code creates ten evenly spaced representative checkpoints over all 120,000 updates, resulting in a 12,000-update interval. It evaluates 16 episodes in 16 environments and pauses training during evaluation.

The current checkpoint contains more state than the reference, but there is no complete training-resume path restoring replay, RNG state, counters, and self-play state.

### 20. Effective YAML and structured defaults disagree

The current structured defaults do not describe the effective training run in several places:

| Setting | Structured default | Effective YAML |
|---|---:|---:|
| Replay capacity | 10,000 | 100,000 |
| Target interval | 200 | 1,000 |
| Precision | FP32 | BF16 |
| Deterministic mode | enabled | disabled |
| Learner compilation | disabled | enabled |
| Compile mode | `max-autotune` | `default` |
| Evaluation episodes | 10 | 16 |
| Evaluation environments | 4 | 16 |

Hydra applies the YAML values, but the duplicate conflicting defaults make experiments and programmatic construction easy to misinterpret.

Relevant current code:

- `src/atariagent/training/config.py`
- `configs/train_agent.yaml`

## Priority Order for Source Parity

If exact parity with the released reference is the goal, the highest-priority corrections are:

1. Add shift and intensity augmentation.
2. Add the 16-channel dynamics action embedding and layer normalization to both Python and C++ models.
3. Change policy, value, and value-prefix hidden activations from ReLU to ELU.
4. Change the consistency predictor hidden width to 256 and its coefficient to 5.
5. Remove uniform-random warmup behavior and retain searched actions and targets from the start.
6. Reanalyze from learner step zero.
7. Reproduce the reference 200-update delayed target publication behavior.
8. Disable target caching or explicitly accept its stochastic-target semantic change.
9. Add a reference-compatible FP16 autocast and gradient-scaling mode.
10. Decide whether environment, tail-bootstrap, masking, and FIFO differences should reproduce source behavior or retain the current more robust behavior.
