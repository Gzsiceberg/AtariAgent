# Asynchronous Reanalysis with Ray

## Goal

Move value and 99% policy MCTS reanalysis out of the learner’s critical path.
The learner remains in the **current driver process** so `tqdm`, checkpoints,
evaluation, and training logs keep their current behavior. Only reanalysis runs
in Ray actors. The synchronous reanalysis path will be removed.

## Ray Setup and Logging

Ray is already a dependency and is useful for actor isolation, bounded task
submission, object-store transfer, failure reporting, and GPU placement.
Initialize it without driver log forwarding or dashboard output:

```python
ray.init(
    log_to_driver=False,
    include_dashboard=False,
    logging_level=logging.ERROR,
)
```

Actors must not print or create progress bars. Route actor diagnostics through
returned metrics; call `ray.shutdown()` in `finally` so workers and CUDA memory
are released cleanly. Configure a dedicated reanalysis GPU when available;
fractional sharing on the learner GPU must be benchmarked for contention.

## Single-Machine Assumptions

The complete program runs on one machine. Start a local Ray runtime rather than
supporting clusters, remote nodes, or distributed replay. Keep the learner and
FIFO replay in the driver and use a small local reanalysis actor pool.

- Transfer CPU batches through Ray's local object store/shared memory; never
  serialize them over the network or duplicate full frame tensors in results.
- Use `ray.put()` once per request/weight snapshot and pass object references.
- Configure the object store for available `/dev/shm` capacity and use the hard
  pending-batch cap to prevent spilling to disk.
- Assign explicit fractional GPU resources to each actor. On the measured
  single RTX 3090, use two actors; four actors saturate the GPU and contend with
  the learner.
- Do not add remote replay/storage actors, autoscaling, placement groups,
  multi-node recovery, or distributed synchronization.
- The driver directly owns actor creation, weight publication, `ray.wait()`,
  result merging, failure handling, and shutdown.

These constraints simplify the implementation and avoid the extra storage and
coordination actors used by the distributed EfficientZero reference.

## Architecture

1. Keep replay sampling, learner optimization, priorities, `tqdm`, checkpointing,
   and evaluation in `scripts/train_muzero.py`.
2. Create two Ray `ReanalysisWorker` instances. Each owns a frozen target
   representation, dynamics, prediction, MCTS, and independent RNG state.
3. Submit CPU `ReanalysisRequest` objects containing a request ID, replay batch,
   and target-weight version. The actor transfers only required tensors to its
   GPU and returns CPU `ReanalysisResult` tensors for value and policy targets.
4. Keep the original CPU batch in the driver. Results return only corrected
   targets and metrics, not duplicate frames. Merge targets, pin/transfer the
   batch, run `MuZeroTrainer.train_step()`, then update replay priorities.
5. Remove target MCTS from `MuZeroTrainer`; it must only optimize batches that
   have already been reanalyzed. Actor startup or failure is fatal rather than
   falling back to synchronous execution.

## Backpressure

Follow EfficientZero’s `QueueStorage` pattern: production stops before queued
work reaches a hard maximum. Use a bounded driver-side pending map instead of
allowing unlimited Ray actor calls.

- `reanalysis_prefetch_batches`: queue depth and hard limit, start at `2`.
- Submit only while `len(pending) < reanalysis_prefetch_batches`.
- When the limit is reached, call `ray.wait(..., num_returns=1)` and train one
  completed batch before sampling/submitting another.
- Never keep more than the configured prefetch depth of original batches or
  object references.
- Track pending depth and Ray object-store bytes; reject duplicate request IDs.
- Apply a timeout to `ray.wait` and fail clearly on actor errors or deadlock.

This follows EfficientZero's bounded-queue approach but uses one small queue
limit because each item contains an Atari frame batch and the driver has only
one producer. Keep the prefetch depth at least as large as the actor count so
all actors can remain busy.

## Driver Target Cache

Replay sampling already randomizes each batch, so select the first
`floor(batch_size * policy_reanalysis_ratio)` samples. Keep one unified cache in
`ReanalysisPipeline`, keyed by stable transition ID, whose entries can contain
a corrected value target, a normalized MCTS policy, or both for the current
target weight version. Before submission, merge cache hits into the retained
batch and send actors explicit value and policy masks containing only unique
misses. After completion, merge searched targets across duplicate positions and
populate the same entry. Clear the cache before every target-weight publication;
never insert a stale result into the new version's cache.

This retains full value coverage, 99% policy coverage, and 50-simulation policy
targets but reuses one noisy policy search when the same transition is sampled
repeatedly within a target interval. It intentionally differs from rerunning
Dirichlet noise for every occurrence.

## Target Weight Updates

Every `target_update_interval`, place one CPU state dictionary in Ray’s object
store and enqueue `set_weights(version, state_ref)` before newer requests. A
each actor preserves its own command order. Broadcast the same object reference
to every actor before dispatching newer work. Tag every result with its weight
version and reject results exceeding the configured maximum lag. Keep the most
recent published target state in the driver so checkpoints do not query or
interrupt the actor.

## Implementation Steps

1. Add async queue, timeout, actor GPU, and weight-lag configuration.
2. Add request/result dataclasses and target-only merge helpers on `ReplayBatch`.
3. Move `ValueTargetNetwork.reanalyze_batch()` behind `ReanalysisWorker` and
   return timing plus target tensors.
4. Add a driver `ReanalysisPipeline` that owns pending batches, `ray.wait`,
   backpressure, weight publication, result validation, and shutdown.
5. Prime the queue before learner updates, then consume one result and submit
   one replacement per update to maintain a steady bounded pipeline.
6. Remove local/synchronous reanalysis and target-network ownership from
   `MuZeroTrainer`; update checkpoint state handling.
7. Keep actor logs disabled and expose queue/actor metrics through the existing
   driver-side `tqdm` postfix or periodic Rich log.

## Tests and Benchmark

- Unit-test hard queue bounds: submitted minus completed never exceeds the
  prefetch depth.
- Test request/result matching, target versions, stale-result rejection,
  timeout, actor failure, deterministic RNG, and clean shutdown.
- Verify 99% policy selection, normalized raw visits, value masks, priorities,
  and replay immutability.
- Add a Ray-local CPU integration test for CI and a real-network GPU benchmark.
- After implementation run:

```bash
uv run pytest
uv run python scripts/benchmark_reanalysis.py \
  --warmup-updates 20 --updates 200 --output benchmarks/async_reanalysis.json
```

Record end-to-end updates/second, actor throughput, learner queue-wait time,
pending-depth maximum, object-store memory, transfer time, target-version lag,
and peak GPU memory. Compare with a synchronous baseline captured before its
removal. Accept the change only if the prefetch depth is never exceeded and
end-to-end updates/second improves on the target hardware.
