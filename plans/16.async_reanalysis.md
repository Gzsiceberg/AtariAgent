# Single-Actor Asynchronous Reanalysis

## Goal

Keep replay, learner optimization, priorities, logging, checkpoints, and evaluation in the driver. Run target value and policy MCTS reanalysis in one local Ray actor without serializing full PyTorch `ReplayBatch` objects.

## Architecture

- Use one `ReanalysisWorker`; multiple actors are not supported.
- Process exactly one replay batch per actor call. There is no `reanalyze_many` or cross-request inference microbatching.
- The actor owns one frozen representation, dynamics, prediction network, and native MCTS instance.
- The driver keeps each original CPU `ReplayBatch`; the actor returns only corrected value and policy targets.
- If `use_target_network_reanalysis` is false, do not initialize Ray or route batches through `ReanalysisPipeline`.
- Actor startup or failure is fatal when reanalysis is enabled; there is no synchronous fallback.

## NumPy Ray transport

Passing a production frame tensor through Ray as a PyTorch object costs roughly 36–52 ms per 60.75 MiB tensor. Passing its zero-copy NumPy view directly costs roughly 3.7–5.9 ms.

For every request, pass only target-reanalysis arrays as NumPy payloads:

- compact frames
- policy and value targets
- policy mask
- optional bootstrap frames, values, discounts, and mask

Do not call `ray.put()` on a nested `ReplayBatch` or request containing Torch tensors. Ray places NumPy buffers in its local object store and exposes read-only arrays to the actor. The actor creates read-only Torch views, transfers one target-only batch to CUDA, and returns small contiguous NumPy target arrays.

Target weight snapshots are also passed as direct NumPy state dictionaries. Keep the corresponding Torch state in the driver for checkpoints.

## Backpressure

`reanalysis_prefetch_batches` is the hard limit for individually queued actor requests. The production default is two:

- one request can execute while one waits in the actor queue
- `submit()` rejects work at the configured limit
- `wait_next()` consumes one result before another request is sampled
- maximum retained payload is `prefetch_batches` replay requests

This keeps the single actor occupied without combining replay batches or increasing model inference batch dimensions.

## Target cache

The single `ReanalysisWorker` owns the target cache. It is keyed by stable transition ID and each entry contains the corrected value target and normalized MCTS policy for the actor's current weight version.

The driver sends original transition IDs and masks without cache preparation. For each request, the worker:

1. groups valid positions by stable transition ID
2. merges actor-cache hits into target arrays
3. selects one position for every missing ID
4. reanalyzes only those unique misses
5. expands each result to duplicate positions and inserts it into the cache

Ray serializes calls to the one actor, so later queued requests naturally see targets cached by earlier calls. No driver reservation, dependency, or pending-result bookkeeping is needed. `set_weights()` clears the actor cache before loading the next target version. The pipeline only mirrors the cache-size metric returned by the actor.

## Weight updates

Actor calls from the driver are ordered:

1. already queued old-version reanalysis
2. `set_weights(new_version)`
3. newly submitted reanalysis

Tag every result with its weight version and reject results older than one `target_update_interval`.

## Benchmarks

Hardware: RTX 3090, batch 256, unroll 5, 18 actions, 50 simulations.

### Cold policy reanalysis without cache

| Prefetch depth | Requests/s | Mean actor time | Peak pending payload |
|---:|---:|---:|---:|
| 1 | 0.727 | 1,364 ms | 127.5 MB |
| 2 | 0.744 | 1,341 ms | 255.1 MB |
| 4 | 0.735 | 1,359 ms | 510.1 MB |

Depth two gives the best measured throughput and remains the default. Larger queues increase latency and memory without improving actor computation.

### Cached production benchmark

For 200 updates over a 10,000-transition replay:

| Metric | Previous multi-actor Torch pipeline | Single actor + NumPy |
|---|---:|---:|
| Updates/s | 5.91 | 9.30 |
| Policy roots searched | 11,321 | 10,000 |
| Search reduction | 26.8x | 30.7x |

Serialized actor requests naturally reuse all targets produced by earlier queued requests.

The actor still receives the complete CPU request because it alone knows the cache contents. For requests containing misses, it transfers the complete contiguous frame arrays to CUDA but passes miss-only policy and bootstrap masks into `reanalyze_batch()`, so cached positions never run value inference or MCTS. A benchmark of compact CPU gathering and miss-only H2D transfer found it slower for cold requests and neutral for partial requests; contiguous whole-batch transfer is cheaper than advanced CPU frame gathering relative to MCTS cost. Fully cached requests bypass CUDA transfer and `reanalyze_batch()` entirely.

### Small asynchronous benchmark

Batch 8, two simulations, 200 updates:

- previous async pipeline: 85.0 updates/s
- optimized single actor: 99.3 updates/s
- synchronous baseline: 84.6 updates/s
- optimized speedup over synchronous: 17.4%

Results are written locally to:

- `benchmarks/reanalysis_actor_pool.json`
- `benchmarks/target_cache.json`
- `benchmarks/async_reanalysis.json`

## Validation

Tests cover:

- direct NumPy request/result transport
- single-actor one-request-at-a-time processing
- hard prefetch bounds
- request/result matching
- actor-owned cache reuse across queued requests
- actor cache clearing on target-weight updates and stale-result rejection
- timeout and shutdown behavior
- local Ray target-network integration

Run:

```bash
uv run pytest -q
uv run python scripts/benchmark_reanalysis_pool.py \
  --prefetch-depths 1,2,4 --requests 8 \
  --output benchmarks/reanalysis_actor_pool.json
uv run python scripts/benchmark_target_cache.py \
  --updates 200 --output benchmarks/target_cache.json
uv run python scripts/benchmark_reanalysis.py \
  --warmup-updates 20 --updates 200 \
  --output benchmarks/async_reanalysis.json
```
